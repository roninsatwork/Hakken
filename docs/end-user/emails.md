# Emails From Hakken

> **Product:** Hakken · **Document type:** End-user guide · **Feature area:** Email and delivery preferences
> **Reviewed:** 26 October 2026, 14:38:35 GMT (Europe/London)
> **Source path:** `docs/end-user/emails.md` · **Status:** Current


## What to expect

Hakken uses email for several different jobs: signing in, joining a workspace, reading the weekly digest, hearing about Hakken tasks, and receiving operational or automation messages. These messages do not all have the same delivery timing or subscription controls. This guide explains the current outbound email path and the choices available on your profile. It describes repository implementation reviewed on the date above, rather than confirming that a deployment's email provider and schedules have been tested live.

The former Gmail mailbox is no longer offered. Its automatic watcher and
company Mailbox screen were removed on 9 October 2026; see the
[Gmail retirement note](./gmail-mailbox.md). Outbound email, personal
communication preferences and the Outbox are separate and remain implemented.

Most messages are designed to tell you what happened early, with a link to the relevant record. When a message is generated by an agent, read it in the context of that agent's job. An email reporting a proposed action is not evidence that the action has already happened. Open the relevant record before assuming a run succeeded, a correction went live or a result was independently verified.

## Your communication preferences

Open your profile at `/app/profile` and choose **Communication preferences**. You can also reach the tab at `/app/profile?tab=communication`. It lists the email types you can choose, what they cover and how often to expect them. The current implementation offers the Weekly News Digest and Hakken tasks. Both start on unless you turn them off.

Use the individual control to stop or restart one type. The subscribe-all and unsubscribe-all controls apply to the email types offered on this tab. They do not disable sign-in messages, invitations or every operational message sent by the platform. This distinction matters when an address still receives necessary service messages after optional subscriptions have been turned off.

These are personal preferences. You do not need to be a company administrator to change your own choices, and changing them does not alter a colleague's subscriptions. An administrator managing a workspace is not using this page to set everybody's preferences. If several people want fewer optional messages, each person should review their own profile.

Changing the Hakken tasks email choice also updates the email channel on your non-deleted tasks within the implementation's bounded update. It does not mean the tasks have been cancelled or deleted. Other task channels and the underlying work are separate from email delivery. If you stop task emails, continue checking the task record or other configured channel when the work matters.

## Weekly News Digest

The Weekly News Digest is an issue prepared from the week's reading material. Its stored issue holds an opening and the selected news items, with Helpful content included where available. The issue is written once and used for readers' messages. Delivery depends on the digest-producing job and the Outbox processor; subscribing does not cause an immediate issue to be composed and sent.

The digest uses the language recorded from your app use. English is the fallback before another supported language is recorded. A language change affects future preparation and delivery behavior; it should not be understood as recalling or rewriting an email already sent to your mailbox. When troubleshooting an unexpected language, check the language you last used in Hakken as well as when the message was queued.

The implementation distinguishes test and live issues. Test issues are restricted to super administrators rather than being sent to every subscribed reader. If an operator is still testing the digest, a subscribed company member may therefore receive nothing. A weekly subscription is not proof that a particular week's issue exists or that the sender is configured.

## Hakken tasks and operational messages

Hakken tasks can produce alerts and reports. Their emails use the task's current state when the message is prepared for sending. A task deleted before its queued alert or report is rendered is skipped. That is intentional: a message that no longer refers to active work should not be treated as an unexplained delivery failure.

Collection-needs-attention messages, system health messages, automation emails and agent emails are also recognized by the Outbox. They serve different purposes from optional reading subscriptions. A stopped collection message should explain what requires attention; a system health message points to an operational problem; an automation or agent message reflects the configured workflow or tool action. Do not assume that every kind is visible as a switch on your profile.

Recipient rules belong to the producing workflow or tool. The existence of an Outbox does not authorize an agent to contact anyone it chooses, but it also does not establish a universal rule that every outbound address must already be a workspace member. The Outbox supports both user-associated messages and explicit recipient addresses. Administrators should use the relevant agent, workflow and access documentation when deciding who a particular job may contact.

## Why delivery can wait

Except for sign-in and invitations, outbound email goes through the Outbox. The default Outbox Queue Processing Agent schedule is hourly, and an administrator can change that schedule. Queuing a message does not itself start an immediate send. A message can therefore be correctly waiting even though the work that produced it has finished.

The sender processes messages in batches and limits the time spent on one run. Remaining work waits for the next scheduled run. Temporary delivery failures can be tried again, with a delay before eligibility and a limit on attempts. Those rules reduce repeated messages and uncontrolled retry loops; they are not a guarantee that every email reaches an inbox within one hour.

A provider accepting a message is also different from the reader receiving or opening it. Spam filtering, an incorrect address or a subsequent bounce can affect what happens after submission. If you are expecting a message, check the destination address and spam folder before assuming the original task failed. Repeating the underlying business action just to obtain another notification can create unnecessary work.

If waiting messages are overdue by more than two hours, an hourly watch can notify super administrators in the in-app bell, at most once a day while the condition persists. The alert does not depend on the delayed email queue. Ordinary company members do not need access to the platform's Outbox to report a missing message.

## Unsubscribe links and delivery suppression

Optional messages carry a way to stop their own communication type. A link from a Hakken task email turns off task emails; it is not a request to unsubscribe from the digest as well. Older digest links without a type continue to mean the digest. You can use your profile to turn the offered choices back on later.

The visible unsubscribe page asks for a deliberate confirmation before changing the preference. Mail applications may also offer their own unsubscribe control using the message's one-click header. This path is separate from simply following the ordinary visible link. Treat unsubscribe links as personal: forwarding one can give its recipient the ability to stop that communication for your address.

Bounce and spam-complaint handling is different from a voluntary subscription choice. The platform records suppressed addresses from verified provider events, and the Outbox skips future messages to a suppressed address. Turning a profile switch back on does not erase that suppression. If an address was corrected or a suppression needs investigation, ask the platform operator to inspect the reason rather than repeatedly producing the same email.

A queued optional message is checked again when it is rendered. If you have turned that type off, it can be skipped even though it was added before you changed the preference. This protects your current choice while also explaining why queue totals and final sent totals need not match.

## Sign-in, invitations and approvals

Sign-in messages and invitations bypass the Outbox so they do not wait for its hourly processing. A problem signing in should therefore be investigated separately from a backlog of digest or task messages. Sign-in links may lead to a confirmation page before the one-use link is spent; some environments use a typed one-time code. Follow the actual sign-in screen for your deployment.

An invitation identifies the workspace and the account address being invited. If it is unexpected, verify it through a known contact before using it. Do not share a sign-in code or a one-use link to help somebody troubleshoot: that can grant access rather than merely reveal an error.

Where an agent or workflow needs approval, use the linked application record to review the proposed work and its current status. This guide does not change the approval rules, expiry policy or permissions of those systems. An email notification is a pointer to that decision, not permission to bypass it.

## Help for administrators

Platform super administrators can inspect **Admin → Content → Outbox** at `/admin/content/outbox`. The list and individual message view show delivery state, type and relevant details. A message detail can show its rendered preview or why it would be skipped, the sender address and next scheduled run. This is a platform administration surface, not a company-admin email mailbox.

When asking for support, provide the message type, approximate expected time, affected task or workflow and the visible error if there is one. Do not include a sign-in link, unsubscribe token, provider API key or another person's email body. The [Email System developer guide](../developer/email-system.md) explains the delivery states and failure boundaries for maintainers. [Tasks And Notifications](./tasks-and-notifications.md) covers the separate in-app notification system, whose bell can remain useful when email is delayed.


## How the weekly issue is produced

The Weekly Digest agent prepares an issue from a recent seven-day content
window. It reads a bounded set of News stories, with Google updates given
priority, together with newly published Knowledge titles and eligible Helpful
content. The opening is written from that material using the agent's
configured instructions and model. The issue is a selection, not a complete
archive of everything published anywhere that week.

There must be at least one News item in the material. A week containing only
new Knowledge or Helpful content does not produce an issue in the current
implementation. An empty inbox therefore does not establish that your
subscription is off or the Outbox is broken. The production run can also
stop when its agent is missing or its spend limit has already been reached.

The agent asks its model to choose up to five useful News stories. A fallback
can retain all the supplied stories when the model response does not provide
usable selections. Do not rely on exactly five cards in every issue. The
email renderer has its own display limits and links back to News for more.
Helpful content uses its reader summaries and original links, rather than
republishing the full source articles inside the digest.

Test and Live are materially different. A Test issue is for super
administrators with an email address, and another Test run can create another
issue. A Live issue targets users with an address across the platform; optional
subscription and suppression checks are applied before sending. Even an opted-out
user can have a queued row that ends up Skipped, providing an explanation in
the Outbox. Queue counts are not counts of subscribed recipients or delivered
messages.

In Live, a normal second run in the same ISO week sees the saved issue and
stops. This helps prevent repeated weekly mail; it is not proof that a
previous interrupted run finished queuing every recipient. The issue is saved
before recipient pages are processed. If production stops part-way, an operator
must inspect that issue, the producing run and its queue rows before deciding
how to recover. Repeatedly pressing Run is not a documented repair.

Translation is attempted before queueing, but an unavailable, disabled or
unsuccessful Translator can leave the English opening as fallback. The
recipient's saved language and the translations actually available at rendering
time determine what is shown. A successful production run does not mean a
human has checked every translated phrase, nor that every queued message has
already been sent. This review performed no production run, translation call
or email send.

## Sender Identity And Delivery Evidence

A sender preview is configuration evidence, not domain verification or mailbox delivery. Platform Outbox can use a dedicated sender before general deployment/stored defaults; auth and retained invite paths have their own timing and precedence. An invite can report simulated success when its API key is absent, while an ordinary queued message remains subject to the Outbox's actual delivery rules. Ask an operator to inspect the message's recorded state when receipt matters; changing a visible sender name does not repair old integrations or rewrite messages already sent.
