# Tasks And Notifications

> **Product:** Hakken · **Document type:** User guide · **Feature area:** Generic tasks and in-app notifications
> **Reviewed:** 26 October 2026, 10:17:44 GMT (Europe/London)
> **Source path:** `docs/end-user/tasks-and-notifications.md` · **Status:** Current

Tasks are work items that Hakken holds for a named person or workspace. They are
not approvals: nothing waits on a task before continuing. A task is simply a
piece of follow-up work that should stay visible until somebody finishes,
reopens, or cancels it.

Notifications are in-app alerts for one person. They appear in the header bell
and can link to the screen that needs attention, such as the Tasks page.

## Where To Find Tasks

Open `/app/tasks` from the app sidebar. The page shows work for the current
workspace and can switch between:

- Everyone: all tasks in the workspace.
- Mine: tasks assigned to you.

Tasks are grouped by due date:

- Overdue
- Today
- This week
- Later
- Done
- Cancelled

The task sidebar entry does not currently carry an open-task count. The header bell has its own unread-notification count; it is not a count of unfinished tasks.

## Creating A Task

Use **New task** on `/app/tasks` to add a manual task. A task needs a title. The current inline form offers an assignee and due date. The underlying task record
can also carry:

- an assignee
- a due date
- detail text
- a source link when another part of Hakken created it

The assignee picker only shows members of the current workspace. A task can
also be left unassigned.

## Working A Task

From the task row you can:

- mark an open task done
- reopen a done or cancelled task
- cancel an open task
- open the source link when one is available

Cancelled tasks are kept as history rather than deleted. This matters when a
workspace needs to see that a follow-up was raised and deliberately dropped.

## Where Tasks Come From

People can create tasks manually, but Hakken can also raise them from other
features:

- a phone call that needs follow-up
- older retained records from retired integrations; Gmail watching is no longer an active source
- a confirmed photo action from Ask Hakken or the website widget
- an agent tool call
- a workflow task node

Machine-created tasks show whether they were raised by an agent or workflow.
Follow-up tasks usually link back to the source screen when Hakken has one.

## Notifications

The header bell shows unread in-app notifications. A notification belongs to one
person; reading yours does not clear a colleague's copy.

Notifications can point at `/app/tasks` or another relevant screen. Opening a
notification marks it read. Use **Mark all read** to clear up to 200 unread notifications per press, including records not currently visible in the panel. If more remain, repeat after checking the remaining count.

Notifications are not email and not push notifications. They are in-product
signals only.

## Practical Guidance

Use tasks for follow-up work that should be visible later. Use approvals for
decisions that must block an agent or workflow before it continues.

Before relying on a task generated by Hakken:

- check the source link when available
- confirm the assignee is the right person
- choose the due date on creation when timing matters; the current task row does not offer a general due-date editor
- mark done only when the work is actually complete

## Choosing The Right Kind Of Task

This guide describes the shared workspace work list stored as generic tasks. [Hakken Tasks](./hakken-tasks.md) describes personal recurring questions, reports, alerts and research requests. Those are separate records and workflows. Creating a generic task does not automatically schedule a repeated model run. Completing it does not cancel a personal watcher, and cancelling a personal Hakken task does not prove that a generic follow-up was closed.

A task is also different from a pending approval. An approval is permission for an action that waits; a task is a record of work somebody should do. Marking a task done does not approve an agent tool, resume a halted workflow, send an email or establish that its suggested action happened in another system. Check the source and perform the actual work through the appropriate feature before closing the task.

## Workspace And Access

The Tasks capability must be available to the workspace. Navigation visibility follows the company/module configuration, while backend task operations enforce the module check and current company. Without an active company the list is empty and creation reports that a workspace is required. An empty Mine view can also mean that tasks exist but are unassigned or assigned to colleagues. Switch to Everyone before assuming the work was lost.

The implemented task operations do not restrict state changes to the assignee. They check that the task belongs to the active company; assignment describes responsibility rather than granting exclusive editing rights. The current authenticated module mutation does not add an admin-only role guard. This is a narrower, implementation-specific permission statement than the general platform guidance about oversight roles. Platform owners should review that distinction before promising read-only behavior for every task API.

The assignee picker reads a bounded workspace member list, currently at most two hundred people. A missing name is not conclusive evidence that the person has no account. Machine-created tasks resolve an assignee email within the same bounded company member set; a missing match leaves the task unassigned rather than sending it to another tenant. Check the task's actual assignee after creation instead of relying on the spelling in an agent's output.

## Due Dates And Loaded Results

The page loads thirty tasks at a time, with Show more for additional results. It groups the loaded records after retrieval; headings and order are not an exhaustive due-date report over every stored task. Load more before assessing the whole queue. Switching Everyone/Mine changes the query population and may show fewer records on a page because the backend also rechecks the active company after paging.

Grouping uses calendar days in the viewer's local timezone. Today means before the next local midnight, and This week currently means within seven days from today's start rather than a fixed Monday-to-Sunday reporting period. An undated open task goes into Later. The screen refreshes its time reference each minute, so leaving it open can move work between groups. A creation date entered on screen is saved at local midday, avoiding an unnecessary midnight boundary.

A title is required and may contain up to two hundred characters. Detail text, where a creation path supplies it, is limited to two thousand. The manual screen currently asks for title, assignee and due date rather than every backend field. After successful creation the inline form clears and closes. If it fails, read the error feedback before retrying; a repeated manual request has no universal duplicate-suppression guarantee merely because two titles match.

## Completing, Reopening And Cancelling

Done records keep completion time and the person who completed them. Reopening clears those completion fields and returns the task to Open. Cancelled tasks remain in history; cancellation does not delete the task. The current row exposes status actions and an optional source link, not a full editor for every stored field. There is no universal expiry or automatic deletion period established by the reviewed task handlers.

When another person is assigned, creation writes an in-app notification linking to Tasks. Assigning yourself does not create a redundant assignment notification. Machine-created tasks can notify their assignee because there is no person actor to suppress. Unassigned tasks notify nobody. A notification's presence means the internal writer created it; it is not proof that its recipient read it or completed the work.

## Notification Reading And Troubleshooting

The bell opens a paged feed, fifteen notifications at a time, newest first. Its count is hidden at zero and shows a capped fifty-plus indication when more than fifty unread records exist. That display is intentionally bounded rather than an exact large-inbox census. Opening an item closes the panel and attempts to mark it read; a failed read-mark is silent and the item can remain unread. Reading or marking all read never changes a colleague's notifications.

Notifications are owned by user identity, with optional company context. Changing the active workspace does not turn the notification feed into a shared company inbox. A linked destination can require access you no longer have, so a notification is not an access grant. No browser-push or email delivery is performed by these in-app notification functions; other features' delivery channels have their own guides and preferences.

This review checked the task list, grouping, creation/state handlers, assignment notifications, photo confirmation entry point and notification bell. No real task, notification or provider action was created or executed. Phone, photo and recurring-task guides describe their own additional workflows; no live integration acceptance or complete retention audit is claimed here.

## Personal-Data Lifecycle Cross-Check

The personal-data manifest defines explicit lifecycle treatment in `convex/personalDataService.ts`: personal notifications are ERASE records, while generic tasks are DISSOCIATE records whose work remains after the declared creator/assignee references are cleared. It does not establish an arbitrary free-text scrub or a universal time-based task/notification purge. Read [Governance And Trust](./governance-and-trust.md) for subject-access scope, retained exceptions and the durable erasure worker.
