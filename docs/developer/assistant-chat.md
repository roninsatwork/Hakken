# Assistant Chat Developer Guide

## Purpose and Product Surface

Assistant chat is the primary user-facing AI conversation workflow in Sonae. It lets authenticated users start a conversation, choose an active chat model, set a reasoning effort, dictate prompts through the browser microphone, attach supported documents, and continue a thread with streamed-looking progress states while backend actions generate responses asynchronously. It appears in the main dashboard navigation as `Ask {platformName}` and is implemented under `src/app/(dashboard)/app/assistant/`. The welcome screen is `src/app/(dashboard)/app/assistant/page.tsx`; active conversations are rendered by `src/app/(dashboard)/app/assistant/[threadId]/page.tsx`; the surrounding route layout is `src/app/(dashboard)/app/assistant/layout.tsx`. The sidebar entry is produced by `src/ui/components/layout/SidebarNavigation.tsx`.

This document describes the current implementation, not planned behavior. It should be read alongside `docs/developer/upload-and-knowledge-policy.md`, `docs/developer/ai-provider-tool-extension.md`, `convex/chat.ts`, `convex/chatService.ts`, `convex/ai.ts`, `convex/knowledge.ts`, `convex/knowledgeActions.ts`, `convex/aiPromptAssembly.ts`, and `convex/aiModelService.ts` before changing chat behavior. The user interface and the backend both enforce important constraints, so future edits should not rely on client-side validation alone.

## Main Routes and Components

The entry screen in `src/app/(dashboard)/app/assistant/page.tsx` renders an `AssistantHero`, an `AssistantComposer`, and `AssistantModals`. It owns prompt text, pending files, drag state, upload status, model dropdown state, thinking-level state, and microphone permission errors. When a user submits from the welcome screen, the page creates a new thread by calling `api.chat.createThread`, uploads any pending files through `api.chat.generateChatUploadUrl`, records uploaded documents with `api.knowledge.saveChatDocument`, sends the first user message through `api.chat.sendMessage`, and then navigates to `/app/assistant/{threadId}`.

The active thread route in `src/app/(dashboard)/app/assistant/[threadId]/page.tsx` reads messages with `api.chat.getMessages` and thread-scoped documents with `api.knowledge.getThreadDocuments`. It renders `ChatMessage` rows from `src/ui/components/chat/ChatMessage.tsx`, displays `SwarmStatusCard`, shows an ingestion progress block while thread documents are pending or processing, and keeps a fixed bottom composer through `src/ui/components/chat/ChatInput.tsx`. The page derives the thinking indicator from the last message: if the last stored message belongs to the user, the assistant is treated as currently generating. A separate optimistic message state is used while a new message is being submitted and before the database result catches up.

`ChatInput` mirrors the welcome composer for continued conversations. It supports drag-and-drop upload, a file picker, voice dictation through `src/hooks/useVoiceToText`, active model selection via `api.aiModels.getActiveModels` with `useCase: "chat"`, and a thinking-level selector with `NONE`, `LOW`, `MEDIUM`, and `HIGH`. The autonomous mode flag exists but is currently fixed to false in both the welcome page and the active composer. If that flag is later exposed, note that `api.chat.sendMessage` already routes `thinkingLevel: "SWARM"` to `internal.swarmActions.executeSwarmObjective`.

## Data Model and Storage

The core tables are defined in `convex/schema.ts`. Conversations are stored in `threads`, messages in `messages`, files and vector state in `knowledgeDocuments` and `knowledgeChunks`, configured models in `aiModels` and `aiModelDefaults`, active rules in `aiRules`, companies in `companies`, users in `users`, and safety events or administrative actions in `auditLogs`. Thread records include `userId`, optional `companyId`, optional `agentId`, optional `widgetId`, title, creation time, and update time. Message records include `threadId`, `role`, `content`, creation time, optional `attachments`, token metadata, provider/model metadata, and analytics dimensions copied from the thread.

Chat uploads use Convex storage for the original file. The UI validates chat documents using `validateUploadFile(file, "chatDocument")` from `src/lib/constants/uploads.ts`. Current accepted document formats are PDF, CSV, plain text, legacy Excel, XLSX, and DOCX. The client-side document limit is 50MB. Inline model payload processing in `convex/ai.ts` applies an additional 5MB limit before attaching a file as inline model content. This means a larger accepted document can still be ingested into vector knowledge but may be skipped for inline model context if it exceeds the 5MB inline threshold. Future docs and UI copy should keep that distinction clear.

When a file is saved through `api.knowledge.saveChatDocument`, the knowledge document is attached to the thread. `convex/knowledgeActions.ts` extracts text from PDFs with `pdf-extraction`, DOCX with `mammoth`, and other supported files as UTF-8 text. It chunks the text through `chunkKnowledgeText`, resolves the active embedding model with `internal.aiModels.resolveEmbeddingModelConfigForExecution`, generates Google Vertex embeddings, and stores vectors in `knowledgeChunks`. It marks documents failed when extraction or embedding fails, and `convex/knowledge.ts` exposes status and inspection queries used by the UI and admin knowledge tools.

## Backend Flow

`api.chat.createThread` requires an authenticated user through `requireCurrentUser`. It stores the active company from `getActiveCompanyId(user)`, which means a super admin using company impersonation creates a thread scoped to the impersonated company. The created title is `"New Conversation"` until title generation updates it.

`api.chat.getThreads` returns up to 100 user-owned threads newest first. `api.chat.getMessages` loads a thread, verifies the current user can access it, and returns up to 500 messages in chronological order. `convex/chatService.ts` contains the access helper. Normal authenticated threads are only readable by their owning user. Anonymous widget threads are a separate pathway and are readable only while the associated widget is active. The assistant route uses authenticated user threads, while widget routes use the widget-specific path.

`api.chat.sendMessage` is the key mutation. It rejects content over 10,000 characters, verifies the thread exists, verifies access before heavy attachment lookup, validates stored attachment metadata, rate-limits the thread to 10 user messages per minute, resolves the company or user quota, and writes a soft block assistant response if the plan allocation is exhausted. When quota is available, it increments the relevant user or company usage counter, redacts PII according to `PII_REDACTION_CONFIG` in `systemConfig`, stores the user message with attachment IDs, updates the thread timestamp, optionally swaps the target agent, and schedules the appropriate async action. Agent threads call `internal.agentRuntime.runAgentObjective`; swarm requests call `internal.swarmActions.executeSwarmObjective`; regular chat calls `internal.ai.generateSonaeResponse`. New conversations also schedule `internal.ai.generateThreadTitle`.

`internal.ai.generateSonaeResponse` applies another 10,000 character guard, runs `evaluateAssistantSafety`, and stores a safety refusal plus an `ASSISTANT_SAFETY_REFUSAL` audit log when a request asks for hidden instructions, permission bypass, or cross-tenant access. It then resolves the execution model through `internal.aiModels.resolveModelConfigForExecution` for use case `chat`, waits up to roughly 60 seconds for thread document ingestion to leave pending or processing states, reads recent conversation history, loads the global system prompt, active company rules, and the company prompt, and assembles a system instruction using `buildAssistantSystemInstruction`. Retrieved knowledge is treated as untrusted context through `buildUntrustedKnowledgeContext`; conversation history is also explicitly marked untrusted through `buildUntrustedConversationHistory`.

The RAG path embeds the user query with the active embedding model and searches `knowledgeChunks` across company, global, and thread scopes. Matches are ordered by `orderAssistantKnowledgeMatches`, then fetched and appended to the prompt up to a 32,000-character knowledge budget. Chunks attached to agents are excluded from the normal assistant response context. If the RAG path fails, the error is logged and generation continues without retrieved knowledge. The final response is generated through `generateTextWithResolvedModel`, then persisted with input/output token counts and provider metadata through `internal.chat.saveAssistantMessage`. Provider failures are normalized and stored as a user-facing offline message rather than thrown back into the UI.

## Authorization, Tenancy, and Safety Boundaries

The chat route is available to authenticated dashboard users. The UI does not show an admin-only guard around `/app/assistant`; backend access is enforced by Convex mutations and queries. A user can only read and mutate their own authenticated threads. Company scope is stored on new threads for quotas, rules, model defaults, and knowledge retrieval, but it does not make company-wide thread reading possible. Administrators do not get automatic read access to another user's personal thread through `api.chat.getMessages`.

Tenant behavior enters chat through three places. First, `getActiveCompanyId` sets the thread company at creation. Second, quota resolution checks user plan overrides before company plans, then treats missing plans as unlimited. Third, `generateSonaeResponse` loads company prompts, active rules, company knowledge chunks, and company model defaults. The safety contract in `convex/aiPromptAssembly.ts` explicitly ranks platform isolation and authorization above configured prompts, company prompts, active rules, retrieved knowledge, uploaded files, and user instructions.

The assistant uses deterministic backend validation for file metadata and authorization. Retrieved documents and uploaded files are deliberately wrapped as untrusted material in the model prompt. Do not change this wrapping casually; it is the main defense against prompt injection from files and knowledge sources. Similarly, model selection should remain resolved through stored configuration. Runtime paths should avoid hardcoding model literals except for the documented failsafe in `convex/aiModelService.ts`.

## Error Handling and Edge Cases

The UI restores prompt text and pending files when starting a thread or submitting a message fails. Upload validation errors are shown through `AssistantModals` or `SonaeModal`, not native browser dialogs. Microphone permission failures also use modal feedback. Active threads display loading, empty, ingestion, thinking, and optimistic-submission states, but the current client does not expose a manual retry button for a failed backend AI action. The persisted assistant error message is the main user-visible failure state.

Thread deletion is implemented by `api.chat.deleteThread`. It requires the current user to own the thread, deletes up to 100 messages, then deletes the thread root. There is no loop in that mutation, so a thread with more than 100 messages could leave older message records behind after the thread is removed. That is a known caveat to address before documenting thread deletion as a complete cascading purge. Thread rename only allows the owning user and normalizes blank names to `"Untitled Conversation"`.

Knowledge ingestion can fail because text extraction produced no text, embedding failed, the configured embedding model is incompatible, the Firecrawl key is missing for website ingestion, or an external provider is rate-limited. Assistant generation waits for thread document ingestion for a bounded period and then proceeds. If a document remains stuck past that window, the user may receive an answer without the uploaded file fully represented in vector context, though the file may still be available as inline context if it is small enough and successfully fetched.

## Configuration and Environment

Visible configuration includes `SITE_URL` or `NEXT_PUBLIC_APP_URL` for invite links elsewhere in the app, `RESEND_API_KEY` and `RESEND_FROM_EMAIL` for email delivery, and `FIRECRAWL_API_KEY` for website knowledge ingestion. Assistant chat generation itself depends on AI provider configuration stored in Convex tables and provider service modules such as `convex/vertexProviderService.ts`, `convex/openaiProviderService.ts`, and `convex/anthropicProviderService.ts`. Voice transcription uses `internal.aiModels.resolveModelConfigForExecution` with use case `transcription` and currently routes through Google Vertex in `convex/ai.ts`.

The PII redaction switch is stored as JSON in `systemConfig` under `PII_REDACTION_CONFIG`. The default in `convex/chatService.ts` has redaction disabled but includes masks for email, credit cards, and National Insurance numbers when enabled. Model defaults and fallbacks are stored in `aiModelDefaults`; enabled model records live in `aiModels`.
