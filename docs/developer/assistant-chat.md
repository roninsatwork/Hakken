# Assistant Chat Developer Guide

## Purpose and Product Surface

Assistant chat is the primary user-facing AI conversation workflow in Hakken. It lets authenticated users start a conversation, choose an active chat model, set a reasoning effort, dictate prompts through the browser microphone, attach supported documents and photos, rate finished answers, confirm photo-derived follow-up tasks, and continue a thread while provider text streams into reactive message rows. It appears in the main dashboard navigation as `Ask {platformName}` and is implemented under `src/app/(dashboard)/app/assistant/`. The welcome screen is `src/app/(dashboard)/app/assistant/page.tsx`; active conversations are rendered by `src/app/(dashboard)/app/assistant/[threadId]/page.tsx`; the surrounding route layout is `src/app/(dashboard)/app/assistant/layout.tsx`. The sidebar entry is produced by `src/ui/components/layout/SidebarNavigation.tsx`.

This document describes the current implementation, not planned behavior. It should be read alongside `docs/developer/upload-and-knowledge-policy.md`, `docs/developer/photo-actions.md`, `docs/developer/ai-provider-tool-extension.md`, `convex/chat.ts`, `convex/chatService.ts`, `convex/aiChat.ts`, `convex/aiSpeech.ts`, `convex/photoActionService.ts`, `convex/knowledge.ts`, `convex/knowledgeActions.ts`, `convex/aiPromptAssembly.ts`, and `convex/aiModelService.ts` before changing chat behavior. The user interface and the backend both enforce important constraints, so future edits should not rely on client-side validation alone.

## Main Routes and Components

The entry screen in `src/app/(dashboard)/app/assistant/page.tsx` renders `src/app/(dashboard)/app/assistant/_components/AssistantHero.tsx`, `src/app/(dashboard)/app/assistant/_components/AssistantComposer.tsx`, and `src/app/(dashboard)/app/assistant/_components/AssistantModals.tsx`. It owns prompt text, pending files, drag state, upload status, model dropdown state, thinking-level state, and microphone permission errors. When a user submits from the welcome screen, the page creates a new thread by calling `api.chat.createThread`, uploads any pending files through `api.chat.generateChatUploadUrl`, records non-image uploaded documents with `api.knowledge.saveChatDocument`, sends the first user message through `api.chat.sendMessage`, and then navigates to `/app/assistant/{threadId}`. Images are attached to the message only; they do not become thread knowledge.

The welcome composer is split into small route-local components: `src/app/(dashboard)/app/assistant/_components/AssistantModelSelector.tsx` renders active model choices, `src/app/(dashboard)/app/assistant/_components/AssistantThinkingSelector.tsx` renders the `NONE`, `LOW`, `MEDIUM`, and `HIGH` reasoning choices from `assistantWelcomeUtils.ts`, `src/app/(dashboard)/app/assistant/_components/AssistantUploadStatus.tsx` renders animated upload progress, and `src/app/(dashboard)/app/assistant/_components/PendingFileTray.tsx` shows removable pending files. Shared route-local prop types live in `src/app/(dashboard)/app/assistant/_components/types.ts`. `src/app/(dashboard)/app/assistant/_components/assistantWelcomeUtils.ts` also owns greeting selection, transcript appending, unsupported-file messages, and the guard for whether the welcome thread can start.

The active thread route in `src/app/(dashboard)/app/assistant/[threadId]/page.tsx` reads messages with `api.chat.getMessages` and thread-scoped documents with `api.knowledge.getThreadDocuments`. It renders `ChatMessage` rows from `src/ui/components/chat/ChatMessage.tsx`, displays `SwarmStatusCard`, shows an ingestion progress block while thread documents are pending or processing, and keeps a fixed bottom composer through `src/ui/components/chat/ChatInput.tsx`. `ChatMessage` also renders viewable image thumbnails and the photo-action confirmation chip when `messages.photoActionProposal` is present. The page derives the thinking indicator from the last message: if the last stored message belongs to the user, the assistant is treated as currently generating. A separate optimistic message state is used while a new message is being submitted and before the database result catches up. Pre-reply status comes from the run itself: `generateSonaeResponse` writes `threads.assistantStage` as it enters each real phase (checking, reading files, searching knowledge, writing) and clears it however the run exits, and `src/ui/components/chat/AssistantStagePill.tsx` shows the noted stage through `getPresentableAssistantStage`, falling back to a plain "Thinking..." when no stage is available. This replaced a client-side rotation of invented phrases on a timer, so a label on screen is always a phase actually in progress.

The assistant layout mounts `ChatHistoryList` in the desktop sidebar. The history list calls `api.chat.getThreads`, filters the returned user-owned thread titles client-side, links directly to `/app/assistant/{threadId}`, and exposes inline rename plus modal-confirmed delete controls. Rename calls `api.chat.renameThread` and delete calls `api.chat.deleteThread`; both backend mutations require the current user to own the thread. If the currently viewed thread is deleted, the client routes back to `/app/assistant`.

`ChatInput` mirrors the welcome composer for continued conversations. It supports drag-and-drop upload, a file picker, voice dictation through `src/hooks/useVoiceToText.ts`, active model selection via `api.aiModels.getActiveModels` with `useCase: "chat"`, and a thinking-level selector with `NONE`, `LOW`, `MEDIUM`, and `HIGH`. The autonomous mode flag exists but is currently fixed to false in both the welcome page and the active composer. If that flag is later exposed, note that `api.chat.sendMessage` already routes `thinkingLevel: "SWARM"` to `internal.swarmActions.executeSwarmObjective`.

Live voice is separate from dictation. The assistant routes can open `RealtimeVoiceOverlay`, which calls `api.aiVoiceSession.createRealtimeVoiceSession`, streams microphone and returned audio through the configured live voice path, handles knowledge tool responses, and records completed spoken turns with `api.chat.recordVoiceTurn`. The broader spoken-channel implementation, including phone calls, voice relay tickets, and the shared spoken voice setting, is documented in [Spoken Channels](./spoken-channels.md).

Voice transcription calls `api.aiSpeech.transcribeAudio`. The action requires an authenticated user, normalizes supported audio MIME types, rejects malformed base64 payloads, rejects decoded audio larger than 10MB, and reserves an `aiActionRequests` row before provider execution. The current transcription rate limit is six requests per user per minute. The action resolves the `transcription` model use case without passing a company id, so it currently uses the global transcription default or platform fallback rather than a tenant-specific model override.

## Data Model and Storage

The core tables are defined in `convex/schema.ts`. Conversations are stored in `threads`, messages in `messages`, files and vector state in `knowledgeDocuments` and `knowledgeChunks`, configured models in `aiModels` and `aiModelDefaults`, active rules in `aiRules`, companies in `companies`, users in `users`, AI action reservations in `aiActionRequests`, and safety events or administrative actions in `auditLogs`. Thread records include `userId`, optional `companyId`, optional `agentId`, optional `widgetId`, optional `widgetAccessTokenHash`, title, creation time, and update time. Message records include `threadId`, `role`, `content`, creation time, optional `attachments`, token metadata, provider/model metadata, and analytics dimensions copied from the thread.

Chat uploads use Convex storage for the original file. The UI validates chat documents using `validateUploadFile(file, "chatDocument")` from `src/lib/constants/uploads.ts`. Current accepted document formats are PDF, CSV, plain text, legacy Excel, XLSX, and DOCX. The client-side document limit is 50MB. Inline model payload processing in `convex/aiChat.ts` applies an additional 5MB limit before attaching a file as inline model content. This means a larger accepted document can still be ingested into vector knowledge but may be skipped for inline model context if it exceeds the 5MB inline threshold. Future docs and UI copy should keep that distinction clear.

When a file is saved through `api.knowledge.saveChatDocument`, the knowledge document is attached to the thread. `convex/knowledgeActions.ts` extracts text from PDFs with `pdf-extraction`, DOCX with `mammoth`, and other supported files as UTF-8 text. It chunks the text through `chunkKnowledgeText`, resolves the active embedding model with `internal.aiModels.resolveEmbeddingModelConfigForExecution`, generates Google Vertex embeddings, and stores vectors in `knowledgeChunks`. It marks documents failed when extraction or embedding fails, and `convex/knowledge.ts` exposes status and inspection queries used by the UI and admin knowledge tools.

## Backend Flow

`api.chat.createThread` requires an authenticated user through `requireCurrentUser`. It stores the active company from `getActiveCompanyId(user)`, which means a super admin using company impersonation creates a thread scoped to the impersonated company. The created title is `"New Conversation"` until title generation updates it.

`api.chat.getThreads` returns up to 100 user-owned threads newest first. `api.chat.getMessages` loads a thread, verifies the current user can access it, and returns up to 500 messages in chronological order. `convex/chatService.ts` contains the access helper. Normal authenticated threads are only readable by their owning user. Anonymous widget threads are a separate pathway and are readable only while the associated widget is active and the caller presents the matching widget access token for the thread. The assistant route uses authenticated user threads, while widget routes use the widget-specific path.

`api.chat.sendMessage` is the key mutation. It rejects content over 10,000 characters, verifies the thread exists, verifies access before heavy attachment lookup, validates stored attachment metadata, rate-limits the thread to 10 user messages per minute, resolves the company or user quota, and writes a soft block assistant response if the plan allocation is exhausted. When quota is available, it increments the relevant user or company usage counter, redacts PII according to `PII_REDACTION_CONFIG` in `systemConfig`, stores the user message with attachment IDs, updates the thread timestamp, optionally swaps the target agent, and schedules the appropriate async action. Anonymous widget threads are the exception to dynamic agent swapping: if `dynamicAgentId` would change the thread agent, the mutation rejects the message with `Unauthorized: Widget conversations cannot switch agents`. Agent threads call `internal.agentRuntime.runAgentObjective`; swarm requests call `internal.swarmActions.executeSwarmObjective`; regular chat calls `internal.aiChat.generateSonaeResponse`. New conversations also schedule `internal.aiChat.generateThreadTitle`.

`internal.aiChat.generateSonaeResponse` applies another 10,000 character guard, runs `evaluateAssistantSafety`, and stores a safety refusal plus an `ASSISTANT_SAFETY_REFUSAL` audit log when a request asks for hidden instructions, permission bypass, or cross-tenant access. It then resolves the execution model through `internal.aiModels.resolveModelConfigForExecution` for use case `chat`, waits up to roughly 60 seconds for thread document ingestion to leave pending or processing states, reads recent conversation history, loads the global system prompt, active company rules, and the company prompt, and assembles a system instruction using `buildAssistantSystemInstruction`. Retrieved knowledge is treated as untrusted context through `buildUntrustedKnowledgeContext`; conversation history is also explicitly marked untrusted through `buildUntrustedConversationHistory`.

The RAG path uses the shared hybrid retrieval spine in `convex/knowledgeRetrieval.ts`: vector and scoped keyword results are fused per company, global, and thread scope, with bounded rated-answer priors when enabled. Winners are fetched and appended to the prompt up to a 32,000-character knowledge budget. Chunks attached to agents are excluded from normal assistant response context. If retrieval fails, the error is logged and generation continues without retrieved knowledge.

`generateTextWithResolvedModel` receives an `onText` callback for ordinary text replies. Google Vertex, OpenAI, Anthropic, and OpenRouter assistant adapters honor it; structured-output calls with `jsonSchema` stay on their non-streaming path. `convex/aiChat.ts` accumulates fragments and uses `shouldFlushStreamedText` to write at most every 250 ms or once 120 pending characters accumulate. The first flush calls `startStreamingAssistantMessage`, later flushes call `appendStreamingAssistantMessage`, and completion calls `finishStreamingAssistantMessage` with final text, tokens, provider/model metadata, and evidence. A short answer that never reaches a partial flush uses the existing single-write mutation.

Streaming is stored in Convex rather than served through an HTTP SSE endpoint to the browser. `ChatMessage` and the widget use `useSmoothStreamText` with pure pacing from `src/lib/streamReveal.ts`: base reveal is 90 characters per second, backlog acceleration keeps display lag near 1.2 seconds or less, and a closed stream finishes its remaining reveal within about 400 ms. Only a row first seen while streaming animates; completed history mounts in full. The caret, feedback controls, and timestamp follow the visible reveal rather than the raw row. A mid-stream provider failure finalizes the existing row with partial text plus the offline notice. If an action dies without cleanup, `useStreamPresentation` turns a row older than ten minutes into the explicit stalled state. Keep token accounting and finalization on every exit path.

Provider-neutral chat generation is currently more mature for text-only prompts than for inline file payloads. `generateSonaeResponse` appends any small attached blobs as `inlineData` content before adding the text prompt. The Google adapter accepts text and inline media parts, while the OpenAI, Anthropic, and OpenRouter adapters currently reject non-text content through `assertTextOnlyContents`. If one of those chat defaults receives inline attachments, the action can fall into the normalized provider-failure path even though text-only prompts for the same model work. Keep this distinction aligned with `docs/developer/ai-provider-tool-extension.md` when expanding adapter support.

## Message Feedback

`MessageFeedbackControls` appears only for completed, non-system assistant messages when `SELF_IMPROVEMENT_CONFIG.endUserFeedback` is enabled. `convex/messageFeedback.ts` requires thread ownership, accepts positive or negative ratings plus bounded labels and comment data, and lets one user update rather than stack ratings for a message. The first 20 ratings per user in a rolling day count toward learning; later ratings are retained but do not move learning counters.

Ratings update feedback counters only for company memories recorded in the answer's evidence and feed the company memory sweep. Comment text remains untrusted stored text and is never inserted into prompts. Keep the switch enforced in the mutation as well as the UI so stale clients cannot continue collecting feedback after an operator disables it.

Chat-log cost displays use `src/lib/chatTelemetry.ts`. Those helpers total stored input/output token fields and estimate GBP display cost from fixed USD rates, a hardcoded GBP/USD conversion, and a simple `modelUsed` name check that treats names containing `pro` as pro-priced. This is an operational estimate for admin chat-log screens, not a billing ledger; billing or cost-accounting changes should use provider pricing configuration and backend cost records instead of these display helpers.

## Swarm Runtime Notes

The swarm path is implemented but not currently exposed as a normal user-selectable mode because the autonomous mode flag in the chat UI is fixed to false. Keep the implementation documented because `api.chat.sendMessage` can already route `thinkingLevel: "SWARM"` to `internal.swarmActions.executeSwarmObjective`, and `SwarmStatusCard` is mounted on active assistant threads.

`convex/swarmRuntime.ts` owns the lightweight status log contract. It stores `swarmLogs` rows with `threadId`, message text, status, display order, optional heading flag, and creation time. `api.swarmRuntime.getSwarmLogs` returns ordered logs for the owning authenticated thread user. It also allows anonymous widget threads that have a widget id and no user id, which keeps widget-side status display possible without opening ordinary user threads. Missing threads, non-owners, and unrelated users receive an empty list rather than thread details. If this query is tightened to use the same widget access token contract as normal chat reads, update the widget iframe and this guide together.

Internal swarm helpers append logs, update log status, clear all logs for a thread, load company context for the thread, and find the hardcoded demo-agent set by name. `internal.swarmActions.executeSwarmObjective` clears previous logs, writes an orchestration heading, loads those demo agents, builds a tenant-aware memory payload, optionally retrieves company knowledge for the architect agent, runs each micro-agent through Google Vertex generation with retry wrappers, records `SWARM MICRO-EXECUTION` agent logs, and saves the final micro-agent output back as the assistant message.

Important caveats:

- The demo-agent lookup depends on named global agents such as `Market Sourcing Agent`, `Internal Platform Architect`, `Verification Agent`, `Financial Modeler`, and `Executive Synthesis Agent`.
- If no demo agents are present, the user-facing assistant message says the swarm failed and asks for the seed command.
- The swarm path resolves model configuration through stored model records for the `workflow` use case, but it still uses Google Vertex provider helpers directly.
- `getSwarmLogs` currently reads up to 10,000 logs for a thread, and `src/analytics-read-drift.test.ts` tracks that as a bounded-runtime-log item to revisit.
- Thread purges cascade related swarm logs; keep that relationship aligned with `docs/developer/data-retention-and-purges.md`.

## Authorization, Tenancy, and Safety Boundaries

The chat route is available to authenticated dashboard users. The UI does not show an admin-only guard around `/app/assistant`; backend access is enforced by Convex mutations and queries. A user can only read and mutate their own authenticated threads. Company scope is stored on new threads for quotas, rules, model defaults, and knowledge retrieval, but it does not make company-wide thread reading possible. Administrators do not get automatic read access to another user's personal thread through `api.chat.getMessages`.

Tenant behavior enters chat through three places. First, `getActiveCompanyId` sets the thread company at creation. Second, quota resolution checks user plan overrides before company plans, then treats missing plans as unlimited. Third, `generateSonaeResponse` loads company prompts, active rules, company knowledge chunks, and company model defaults. The safety contract in `convex/aiPromptAssembly.ts` explicitly ranks platform isolation and authorization above configured prompts, company prompts, active rules, retrieved knowledge, uploaded files, and user instructions.

The assistant uses deterministic backend validation for file metadata and authorization. Retrieved documents and uploaded files are deliberately wrapped as untrusted material in the model prompt. Do not change this wrapping casually; it is the main defense against prompt injection from files and knowledge sources. Similarly, model selection should remain resolved through stored configuration. Runtime paths should avoid hardcoding model literals except for the documented failsafe in `convex/aiModelService.ts`.

## Error Handling and Edge Cases

The UI restores prompt text and pending files when starting a thread or submitting a message fails. Upload validation errors are shown through `AssistantModals` or `SonaeModal`, not native browser dialogs. Microphone permission failures also use modal feedback. Active threads display loading, empty, ingestion, thinking, and optimistic-submission states, but the current client does not expose a manual retry button for a failed backend AI action. The persisted assistant error message is the main user-visible failure state.

Thread deletion is implemented by `api.chat.deleteThread`. It requires the current user to own the thread, deletes up to 100 messages, then deletes the thread root. There is no loop in that mutation, so a thread with more than 100 messages could leave older message records behind after the thread is removed. That is a known caveat to address before documenting thread deletion as a complete cascading purge. Thread rename only allows the owning user and normalizes blank names to `"Untitled Conversation"`.

Knowledge ingestion can fail because text extraction produced no text, embedding failed, the configured embedding model is incompatible, the Firecrawl key is missing for website ingestion, or an external provider is rate-limited. Assistant generation waits for thread document ingestion for a bounded period and then proceeds. If a document remains stuck past that window, the user may receive an answer without the uploaded file fully represented in vector context, though the file may still be available as inline context if it is small enough and successfully fetched.

## Configuration and Environment

Visible configuration includes `SITE_URL` or `NEXT_PUBLIC_APP_URL` for invite links elsewhere in the app, `RESEND_API_KEY` and `RESEND_FROM_EMAIL` for email delivery, and `FIRECRAWL_API_KEY` for website knowledge ingestion. Assistant chat generation itself depends on AI provider configuration stored in Convex tables and provider service modules such as `convex/vertexProviderService.ts`, `convex/openaiProviderService.ts`, and `convex/anthropicProviderService.ts`. Image-bearing chat turns require a compatible `vision` model default; the current executable image path is Google Vertex. Voice transcription uses `internal.aiModels.resolveModelConfigForExecution` with use case `transcription`, no company id, and currently routes through Google Vertex in `convex/aiSpeech.ts`. Real-time spoken sessions use the `realtime` model default and the relay or provider configuration documented in [Spoken Channels](./spoken-channels.md). Keep transcription provider calls behind the `assertValidTranscriptionPayload` and `internal.aiActionRequests.reserve` guardrails so malformed, oversized, or rapid repeated audio requests do not reach the provider.

The PII redaction switch is stored as JSON in `systemConfig` under `PII_REDACTION_CONFIG`. The default in `convex/chatService.ts` has redaction disabled but includes masks for email, credit cards, and National Insurance numbers when enabled. Model defaults and fallbacks are stored in `aiModelDefaults`; enabled model records live in `aiModels`.
